### 2. Correctness (30 points)

- **API Usage:**  
  - `veh.HMMWV_Full()` usage is correct.  
  - Contact method, collision type, visualization types, and tire model are set properly.  
  - Terrain patch material is created with friction and restitution set correctly.  
  - Visualization system is correctly initialized and attached to the vehicle.  
  - Driver deltas are set proportional to render step size, which is good practice.  
  - Sensor creation and filter pushing follow documented patterns.  
  - The simulation loop correctly synchronizes and advances all components.  
  - The use of `vehicle.GetVehicle().GetMass()` is correct to print vehicle mass.  
  - The use of `manager.Update()` to update sensors is correct.  
  - The GPS data logging is done correctly by accessing the most recent GPS buffer.  

- **Potential issues:**  
  - The `offset_pose` for sensors is created using `chrono.ChFramed` which is not a documented class in the provided API. The documentation shows `chrono.ChCoordsysd` or `chrono.ChCoordsysD` for poses. This may cause an error or unexpected behavior. The correct class for pose is `chrono.ChCoordsysd` (or `ChCoordsysD`), not `ChFramed`.  
  - The `offset_pose` is passed as the third argument to sensors, which expects a pose. Using an undefined or incorrect class is a significant API misuse.  
  - The `gps` sensor is initialized with a position vector (latitude, longitude, altitude) as the 4th argument, which is correct.  
  - The `driver_inputs` are modified after calling `driver.GetInputs()`, but the code only sets throttle and steering before 6 seconds, and braking after 6 seconds. However, it does not reset throttle or steering to zero after 6 seconds, which may cause unintended inputs (e.g., throttle remains at 0.5). This is a logical error.  
  - The `driver_inputs` object is modified but not explicitly passed back to the driver; however, since `driver.Synchronize()` is called with time and `vehicle.Synchronize()` with `driver_inputs`, this is acceptable.  
  - The `vis.Synchronize()` is called with `driver_inputs`, but the visualization system typically expects the time and vehicle state, not driver inputs. This is a minor misuse but unlikely to cause failure.  
  - The `vehicle.SetChassisCollisionType(chassis_collision_type)` is set to `veh.CollisionType_NONE`, which disables chassis collision. This is acceptable but may limit simulation realism. No deduction since it is intentional.  
  - The `vehicle.GetSystem().SetCollisionSystemType(chrono.ChCollisionSystem.Type_BULLET)` is called after vehicle initialization. This is acceptable but generally should be set before initialization for consistency. Minor issue.  

**Deductions:**  
- Incorrect use of `chrono.ChFramed` for sensor offset pose: **-15 points** (significant API misuse).  
- Logical error in driver input resetting after 6 seconds (throttle not reset): **-10 points**.  
- Minor misuse of `vis.Synchronize()` with driver inputs instead of time or vehicle state: **-5 points**.  
- Setting collision system type after vehicle initialization (minor but non-critical): no deduction (minor).
