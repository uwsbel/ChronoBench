### 2. Correctness (30 points)

- **API Usage:**
  - `system.Set_G_acc()` is used, but the correct method name per PyChrono API is `Set_G_acc` (underscore). The code uses `Set_G_acc`, which is correct.  
  - `ChBehavior` is subclassed for `ParticleEmitter`. However, **`ChBehavior` is not a documented PyChrono class** in the provided API docs. PyChrono does not have a `ChBehavior` base class for user-defined behaviors. This is a **significant API misuse**.  
  - The emitter calls `emit_particle()` which creates spheres and adds them to the system. However, the spheres' mass is set after creation, but `ChBodyEasySphere` already sets mass based on density and radius. Setting mass directly without updating inertia or other properties can cause inconsistency.  
  - `sphere.SetWvel()` is used to set angular velocity, which is correct.  
  - `sphere.SetCollide(True)` is called, but the correct method per API is `EnableCollision(True)`. This is an **incorrect API usage** that could lead to collisions not being enabled properly.  
  - The container box also uses `SetCollide(True)` instead of `EnableCollision(True)`.  
  - `system.Get_BodyList()` is used in `create_attraction_forces()`. The API does not document a method named `Get_BodyList()`. The correct way to iterate bodies is usually through `system.Get_bodylist()` or `system.Get_bodylist()` (case sensitive). This is likely an **incorrect API call**.  
  - The `AttractionForce` class subclasses `chrono.ChForce`, which is not documented in the API. The API does not mention `ChForce` or a method `Apply()`. Forces are usually applied directly to bodies or via `ChForce` subclasses in C++ but not exposed like this in Python. This is a **logical error** in force application.  
  - The force application uses `self.body1.ApplyForce(force)` and `self.body2.ApplyForce(-force)`. The method `ApplyForce()` exists, but forces applied this way are instantaneous and need to be applied each step. The code removes all forces each step and re-adds them, which is consistent.  
  - The `AttractionForce` instances are created every step and added to the system, but never removed. This will cause the system to accumulate forces indefinitely, leading to performance degradation or incorrect simulation behavior. This is a **significant logical error**.  
  - `emitter.Enable()` is called, but `ChBehavior` does not have an `Enable()` method in the API. This is an **incorrect API usage**.  
  - `chrono.ChVectorD` is used, but the API uses `chrono.ChVector3d` or `chrono.ChVectorD` is not documented. This is a **minor inconsistency** but likely acceptable as `ChVectorD` is an alias for double precision vector in PyChrono.  
  - The `force_direction` is normalized correctly, and force magnitude is computed as inverse square law.  
  - The emitter's `DoStep()` method is called manually each loop, which is acceptable given the custom class, but since `ChBehavior` is not a valid base, this is questionable.

**Summary of deductions:**

- Incorrect use of `ChBehavior` base class and related methods: **-15 points**
- Incorrect method `SetCollide(True)` instead of `EnableCollision(True)`: **-15 points**
- Incorrect or non-existent API calls: `Get_BodyList()`, `Enable()`: **-10 points**
- Logical error: accumulation of forces without removal: **-10 points**

Total Correctness deduction: 15 + 15 + 10 + 10 = 50 points, but max deduction is 30, so capped at **-30 points**

- The emitter creates spheres with random positions and velocities each emission, which is fine.  
- The `time_since_last_emission` resets to zero exactly when emission occurs, which can cause timing drift; better to subtract the emission interval instead. Minor optimization opportunity.
