### 2. Correctness (30 points)

- **API Usage:**  
  - The vehicle is configured correctly with contact method, collision type, visualization types, tire model, and step sizes.  
  - The terrain patch material is created with friction and restitution set properly.  
  - The visualization system is used correctly.  
  - The PID controller logic is sound, and the steering input is applied to the vehicle's front axle (`vehicle.GetPart(0)`) which is consistent with typical vehicle API usage.  
  - The simulation loop uses `Advance()` methods rather than `DoStepDynamics()`, which is appropriate for vehicle simulations.  
  - The error calculation for steering uses `vehicle_rot.EulerAngles().z()`. This is a potential issue because `EulerAngles()` returns a tuple of three angles (roll, pitch, yaw), but the API documentation does not guarantee the order or the presence of a `.z()` method on the tuple. In Python, tuples do not have `.z()` attribute. This is a **logical error**. The correct way would be to unpack the Euler angles and use the yaw angle, e.g., `yaw = vehicle_rot.EulerAngles()[2]`.  
  - The `steering_input` is not clamped or limited, which could cause unrealistic steering commands. While not strictly incorrect, it is a best practice to limit control inputs.  
  - The `vehicle.GetPart(0)` usage is somewhat opaque; better would be to use explicit methods like `vehicle.GetSteering()` or `vehicle.GetDriveline()` if available. But this depends on the vehicle API.  
  - The balls are created with `True, True` for visualize and collision, but no explicit material is passed to `ChBodyEasySphere`. The material is set later via `SetMaterial()`, which is acceptable.

  - The `vehicle.GetSystem().SetCollisionSystemType(chrono.ChCollisionSystem.Type_BULLET)` is set after vehicle initialization. According to best practices, collision system type should be set before initialization to ensure proper setup. This could cause unexpected behavior.
