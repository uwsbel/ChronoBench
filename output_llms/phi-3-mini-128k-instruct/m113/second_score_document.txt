### 2. Correctness (30 points)

- **Incorrect use of API:**
  - The terrain is initialized with `veh.SCMTerrain(vehicle.GetSystem(), scm_soil_params, terrain_height_map)` **before** the vehicle is created. Since `vehicle` is not defined yet, this will raise a `NameError`.
  - The correct order should be: create the vehicle first, then get its system, then create terrain.
  - The script calls `vehicle.SetInitPosition(...)` and then `vehicle.Initialize()`, which is correct.
  - The collision system type is set on `vehicle.GetSystem()` after vehicle initialization, which is acceptable but better to set before initialization.
  - The script calls `vehicle.GetVehicle().EnableRealtime(True)`. The method `GetVehicle()` returns the underlying vehicle object, but `EnableRealtime()` is a method of the vehicle system or visual system? According to API, `EnableRealtime()` is a method of `ChSystem` or `ChVisualSystemIrrlicht`. This call is ambiguous and likely incorrect.
  - The script sets driver inputs twice in the loop:
    ```python
    driver_inputs = driver.GetInputs()
    driver_inputs.SetThrottle(0.8)
    driver_inputs = driver.GetInputs()
    ```
    The second call is redundant and unnecessary.
  - The script does not call `vehicle.GetSystem().DoStepDynamics(step_size)` or equivalent to advance the physics system. Instead, it calls `Advance(step_size)` on vehicle, driver, terrain, and visualization. This is correct for vehicle module-based simulation.
  - **Deduction: 15 points** for the terrain initialization order error and the undefined `vehicle` at that point.
  - **Deduction: 10 points** for the ambiguous or likely incorrect call to `vehicle.GetVehicle().EnableRealtime(True)` and redundant driver input calls.
  - Minor: The collision system type is set after vehicle initialization; better practice is before initialization.
  - **Deduction: 5 points** for minor inaccuracies.

**Total Correctness deduction: 15 + 10 + 5 = 30 points**
