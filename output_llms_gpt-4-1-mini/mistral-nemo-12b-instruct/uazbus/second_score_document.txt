### 2. Correctness (30 points)

- **API usage correctness:**

  - `vehicle.SetChassisCollisionType(chassis_collision_type)` with `CollisionType_NONE` is valid if no chassis collision is desired.

  - Synchronization and advancement calls are in the correct order.  
  - Lane change logic modifies `driver_inputs` after `driver.GetInputs()` but before `driver.Synchronize()`. However, the code modifies `driver_inputs` **after** synchronization and module updates, which is incorrect. The driver inputs should be set **before** `driver.Synchronize(time)` so that the driver module processes the updated inputs. Here, the lane change logic is placed **after** the synchronization calls, so the modified inputs will not affect the current simulation step but only the next one, or possibly not at all if the driver module overwrites inputs. This is a **logical error**.  
  - Also, the lane change logic modifies `driver_inputs` directly, but `driver_inputs` is typically a copy or a read-only snapshot of inputs. The proper way to control driver inputs programmatically is to use driver methods or set inputs via the driver interface, or to subclass the driver. Directly modifying `driver_inputs` may not have the intended effect.  
  - The final `realtime_timer.Spin(step_size)` outside the loop is redundant since the loop already spins each step.  
  - The initial vehicle position is set to (-40, 0, 0.5), which is fine but no explanation is given for this choice.  
  - The terrain patch is created at (0,0,0) with zero height offset, which is consistent.  
  - The patch texture is set to "concrete.jpg" which is a valid data file.  
  - The `driver_inputs` throttle is set to 0.0 at lane change midpoints, but no explicit resetting of throttle to a positive value after that is done, so throttle may remain zero unintentionally.  
  - The braking input is set to 1.0 after the lane changes, which is logical.  
  - The `lane_change_counter` resets after 3 lane change intervals, which is fine.  
  - The `driver_inputs` steering and throttle are set only during lane change intervals; outside those intervals, inputs are not explicitly reset to zero or default, which may cause unintended behavior.  
  - The `driver_inputs` is modified but the driver module is not explicitly told to accept these inputs; this is a **logical error** or at least a misuse of the API.

**Deductions:**  
- **-15 points** for incorrect handling of driver inputs and lane change logic that likely prevents intended behavior.  
- **-5 points** for redundant `realtime_timer.Spin(step_size)` outside the loop.  
- **-5 points** for minor logical issues with throttle/braking input resetting and input modification approach.
