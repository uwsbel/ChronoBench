### 2. Correctness (30 points)

- **API Usage:**  
  - `veh.MAN_10t()` is correctly instantiated and configured.  
  - Contact method and collision system type are set appropriately.  
  - Terrain patch is created with correct material and texture.  
  - Visualization system is properly initialized and attached.  
  - Driver inputs and synchronization calls are correctly ordered.  
  - Step sizes and render steps are correctly computed and used.  
  - Real-time timer is used properly to keep simulation in sync with real time.  

- **Potential issues:**  
  - `vehicle.SetChassisCollisionType(chassis_collision_type)` is called before `vehicle.Initialize()`. According to best practices, collision type should be set before initialization, so this is correct.  
  - `vehicle.SetChassisVisualizationType(vis_type)` and other visualization types are set **after** `vehicle.Initialize()`. This is acceptable and common practice, but the API documentation sometimes suggests setting visualization types before initialization for some vehicle models. However, the vehicle module supports changing visualization types after initialization.  
  - `vehicle.GetSystem().SetCollisionSystemType(chrono.ChCollisionSystem.Type_BULLET)` is called **after** vehicle initialization. This is unusual because collision system type is typically set before system initialization to avoid reinitialization issues. However, since the vehicle internally creates the system, this call may be redundant or ineffective. The vehicle's system is already created with the contact method set, but the collision system type is not guaranteed to be BULLET by default. This could be a minor logical error or unnecessary call.  
  - The `driver.Initialize()` call is made but no initial synchronization of the driver with the vehicle state before the simulation loop is done. Usually, `driver.Synchronize(time)` is called before the loop starts to ensure initial states are consistent. This is a minor logical omission.  
  - The `driver.GetInputs()` call is made before `driver.Synchronize(time)`. According to typical usage, inputs should be fetched after synchronization to get updated inputs. This is a minor logical ordering issue.  
  - The `vis.Synchronize()` call includes `driver_inputs` as a parameter, but the Irrlicht visual system usually only needs time and vehicle reference; passing driver inputs is unnecessary and may be ignored. This is a minor unnecessary API call.  

**Deductions:**  
- 10 points for minor logical errors (driver input ordering, collision system type setting after initialization).  
- 5 points for minor unnecessary API call (passing driver inputs to `vis.Synchronize()`).
