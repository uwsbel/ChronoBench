### 2. Correctness (30 points)

- **API usage correctness:**  
  - Vehicle initialization and parameter setting follow API guidelines.  
  - Terrain parameters and initialization are consistent with SCM terrain usage.  
  - Visualization setup uses `veh.ChWheeledVehicleVisualSystemIrrlicht()`, which is correct for vehicle visualization.  
  - Driver input deltas are calculated correctly based on render step size and response times.  
  - Obstacles are created as `chrono.ChBody()`, collision model cleared and rebuilt properly.  
  - Sensor manager and Lidar sensor are created with correct parameters and filters.  
  - The Lidar offset pose uses `chrono.ChFrameD` and quaternion from angle Z, which is correct.  
  - The Lidar FOV is set with `SetFov` using a `ChCoordsysD` and angles in radians, consistent with API.  
  - Simulation loop calls `Synchronize` and `Advance` on all modules in correct order.  
  - Real-time timer usage is appropriate.  

- **Potential issues:**  
  - The `vehicle.GetSystem().SetCollisionSystemType(chrono.ChCollisionSystem.Type_BULLET)` call is made **after** vehicle initialization. According to best practices, collision system type should be set **before** system initialization to avoid unexpected behavior. This could affect collision detection and performance.  
  - The terrain is created with `veh.SCMTerrain(vehicle.GetSystem())` but the terrain is not added to the system explicitly. However, `SCMTerrain` internally adds itself to the system, so this is acceptable.  
  - The obstacles are fixed bodies but `SetBodyFixed(True)` is used instead of `SetFixed(True)`. According to the API, `SetFixed()` is the standard method to fix bodies. `SetBodyFixed()` is not a documented method and likely a typo or incorrect method call. This is a **significant error** that could cause obstacles to behave incorrectly (not fixed).  
  - The obstacle collision boxes are added with half extents equal to the full size (1,1,1). The API expects half extents for `AddBox()`. This means the boxes are twice as large as intended. This is a **logical error** affecting obstacle size.  
  - The `lidar.SetFov()` call uses `chrono.ChCoordsysD(chrono.ChVectorD(0, 0, 1), chrono.Q_from_AngY(...))` as first argument, but the API expects a float for FOV angles and a float for max range. The signature in the code is inconsistent with the documented API, which usually is `SetFov(horizontal_fov, vertical_fov)`. This may be a misuse or confusion between `SetFov()` and `SetOffsetPose()`. This is a **minor API misuse** that might cause unexpected Lidar behavior.  
  - The `lidar.PushFilter(sensor.ChFilterSave("lidar_data.csv"))` is used without specifying append mode or file path management, which could overwrite data on each run. Minor issue.  
  - The `driver.GetInputs()` is called but the returned inputs are not used directly; instead, `driver.Synchronize()` is called with time, and then `vehicle.Synchronize()` is called with `driver_inputs`. This is correct usage.  
  - The `vehicle.SetChassisCollisionType(chassis_collision_type)` is set to `veh.CollisionType_NONE`, which disables chassis collision. This is acceptable but may limit collision realism. No deduction.  

**Deductions:**  
- Collision system type set after initialization: **-10 points** (important detail affecting simulation correctness)  
- Use of `SetBodyFixed(True)` instead of `SetFixed(True)` on obstacles: **-15 points** (significant API misuse likely causing incorrect obstacle behavior)  
- Obstacle box sizes using full extents instead of half extents: **-10 points** (logical error affecting obstacle size)  
- Minor Lidar FOV misuse: **-5 points**  
- Minor data saving filter usage: **-3 points**  

Total deductions in correctness: 10 + 15 + 10 + 5 + 3 = 43 points, but max deduction is 30 points, so capped at **-30 points**.
