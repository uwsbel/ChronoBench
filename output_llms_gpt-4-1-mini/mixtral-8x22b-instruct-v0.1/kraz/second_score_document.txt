### 2. Correctness (30 points)

- **Use of `veh.Kraz()` and system access**: Correct and consistent with vehicle module usage.  
  **No deduction.**

- **Setting chassis collision type to `veh.CollisionType_NONE`**: This disables chassis collision. While valid, it may affect simulation realism if chassis collisions are expected. However, this is a user choice, not an error.  
  **No deduction.**

- **Setting visualization types**: The call `vehicle.SetChassisVisualizationType(vis_type, vis_type)` passes two arguments, but per the API, `SetChassisVisualizationType` takes a single argument for visualization type. Similarly for other `Set*VisualizationType` calls, the API expects a single argument. The script passes two arguments for some calls (e.g., `SetSuspensionVisualizationType(vis_type, vis_type)`, `SetWheelVisualizationType(vis_type, vis_type)`, `SetTireVisualizationType(vis_type, vis_type)`).  
  This is incorrect usage and could cause errors or unexpected behavior.  
  **Deduct 15 points for incorrect API usage.**

- **`vehicle.GetSystem().SetCollisionSystemType(chrono.ChCollisionSystem.Type_BULLET)`**: Setting collision system type after vehicle initialization is acceptable, but best practice is to set it before initializing the vehicle to ensure all components use the correct collision system. This might cause inconsistent collision behavior.  
  **Minor logical error: -5 points.**

- **`vis.AttachVehicle(vehicle.GetTractor())`**: The vehicle class `veh.Kraz()` does not have a method `GetTractor()`. The correct method to get the vehicle for visualization is `vehicle.GetVehicle()` or simply `vehicle` itself. This will cause an AttributeError at runtime.  
  **Major API misuse: -15 points.**

- **Driver input modification inside the loop**: The script modifies `driver_inputs.m_steering` after calling `driver.GetInputs()`. However, `driver_inputs` is typically a copy or a reference managed by the driver system. Modifying it directly may not affect the driver’s internal state or the vehicle input properly. The correct approach is to implement a custom driver or set inputs via driver methods.  
  This is a logical error that can cause the intended lane change maneuver to fail.  
  **Logical error: -10 points.**

- **Use of `chrono.SetChronoDataPath(chrono.GetChronoDataPath())`**: This line is redundant since it sets the data path to itself. It does no harm but is unnecessary.  
  **Minor inaccuracy: -5 points.**

- **Use of `veh.SetDataPath(chrono.GetChronoDataPath() + 'vehicle/')`**: This concatenation misses a path separator (`/` or `\\`) between the base path and `'vehicle/'`. This could cause incorrect data path resolution on some systems.  
  **Minor inaccuracy: -5 points.**
