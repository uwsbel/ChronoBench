### 2. Correctness (30 points)

- **Use of `veh.UAZBUS()` and `vehicle.GetSystem()`**:  
  Correct usage for vehicle simulation.

- **Setting contact method and collision type**:  
  `vehicle.SetContactMethod(contact_method)` and `vehicle.GetSystem().SetCollisionSystemType(chrono.ChCollisionSystem.Type_BULLET)` are correct and consistent.

- **Tire model and step size**:  
  Tire model set to TMEASY and tire step size set correctly.

- **Visualization system**:  
  `vis.AttachVehicle(vehicle.GetVehicle())` is correct.

- **Driver inputs update logic**:  
  There is a logical flaw here:  
  ```python
  while current_maneuver_index < len(maneuver_profile) and time >= maneuver_profile[current_maneuver_index][0]:
      steering, throttle, braking = maneuver_profile[current_maneuver_index][1], maneuver_profile[current_maneuver_index][2], maneuver_profile[current_maneuver_index][3]
      driver_inputs = veh.ChDriverInputs()
      driver_inputs.m_steering = steering
      driver_inputs.m_throttle = throttle
      driver_inputs.m_braking = braking
      current_maneuver_index += 1
  ```
  This loop advances `current_maneuver_index` as long as the simulation time exceeds the maneuver time points, but it creates a new `driver_inputs` object each iteration and overwrites it. After the loop, only the last `driver_inputs` is used in synchronization. This means that if the simulation time is beyond multiple maneuver points, the driver inputs jump immediately to the last matching profile, skipping intermediate states. This is not a smooth or correct way to interpolate or hold inputs over time.

  Also, `driver_inputs` is not initialized before the loop, so if the simulation time is less than the first maneuver time (0), `driver_inputs` is undefined when used in `vehicle.Synchronize(time, driver_inputs, terrain)` and `vis.Synchronize(time, driver_inputs)`. This will cause a runtime error.

  **This is a significant logical error. Deduct 10 points.**

- **Driver input synchronization**:  
  The driver system is synchronized with time, but the driver inputs are manually created and passed to vehicle and visualization. Normally, the driver system itself provides inputs internally; passing `driver_inputs` manually to vehicle and visualization is unusual and may cause inconsistency.

- **Use of `driver.SetSteeringDelta(render_step_size / 1.0)` etc.**:  
  The division by 1.0 is redundant but harmless.

- **Use of `vis.Synchronize(time, driver_inputs)`**:  
  According to the API, visualization synchronization typically takes time and vehicle state, not driver inputs. Passing driver inputs here is unusual and may be incorrect or unnecessary.

  **Minor incorrect API usage. Deduct 5 points.**

- **Use of `vehicle.SetChassisCollisionType(chassis_collision_type)` with `CollisionType_PRIMITIVES`**:  
  This is acceptable and even noted as a change for better collision.

- **Use of `chrono.SetChronoDataPath(chrono.GetChronoDataPath())`**:  
  This is redundant but not incorrect.

- **Use of `vis.AddLightDirectional()` instead of `vis.AddTypicalLights()`**:  
  The API suggests `AddTypicalLights()` for standard lighting; `AddLightDirectional()` adds a single directional light. This is acceptable but may result in suboptimal lighting.

  **Minor visualization issue. Deduct 2 points (will consider under visualization).**

- **Use of `exit()` in exception block**:  
  `exit()` is a built-in function but better practice is to use `sys.exit()` for clarity. Minor issue.

- **Use of `realtime_timer.Spin(step_size)`**:  
  Correct usage for real-time pacing.
